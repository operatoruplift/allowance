## Preserved product contract

Public routes are `/`, `/demo`, `/developers`, `/brand` and the explanatory private-route boundary. The persistent server supplies authenticated `/login`, `/app`, `/runs/:id`, the durable ledger, two first-party exact-payment merchants and the bounded agent. The local stdio MCP bridge shares the same policy, service, ledger and process lease. Operator keys, wallet keys and provider credentials never enter the public build.

The example allowance remains 0.040000 USDC; snapshot 0.010000; explanation 0.020000; remaining 0.010000. The separately initiated 0.020000 policy probe is denied before signing. Rehearsal settlement and recovery are simulations, not onchain evidence.

## Deployment and activation

The production public surface is [allowanceonsolana.vercel.app](https://allowanceonsolana.vercel.app); source is [operatoruplift/allowance](https://github.com/operatoruplift/allowance). The static deployment is separate from activating the persistent payment backend.

A presence-only configuration check found no configured operator password hash, session secret, payer key source, merchant recipient, trusted fee sponsor, payment/facilitator endpoints, OpenAI key/model or demo wallet. The local `.env.local` contains none of these live-runtime fields. No private value was printed. Funding has not been checked because no payer and merchant accounts are configured. A persistent backend host with a writable volume and HTTPS has not been supplied. Docker is not installed locally, so container execution is unverified.

To activate, supply the persistent host, follow [live setup](live-setup.md), run `npm run setup:operator` privately, configure the mainnet payer/merchant/facilitator/RPC and provider credentials, and run read-only `npm run preflight`. Mainnet payments require both explicit live enablement and `MAINNET_PAYMENTS_ACKNOWLEDGED=true`. A funded smoke additionally requires its command-line confirmation and a separately authorized spending run. Do not put secrets in Git, the public browser, or chat.

## Migration and rollback

No SQLite schema migration or rewrite of stored policies is needed for this release. Existing network, mint, receipt, reservation and request identity values remain authoritative. Keep a consistent database backup before upgrades; deploy a single process with its persistent volume and restart once. Do not run the old devnet-only binary against mainnet records after enabling mainnet; rollback of code and data must use a matching backup and leave signing disabled until all signed or submitted intents are reconciled. Never discard an unresolved hold to roll back a release.

For the static site, a previous Vercel deployment can be promoted independently of the payment database. Keep the current operator backend disabled if its configuration or database consistency is uncertain.
